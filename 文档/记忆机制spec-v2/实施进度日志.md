## 2026-08-13 Step 8：区分“单次模型超时”与“整个任务取消”

### 失败簇与根因

- Django 严格 Paw 样本：读到目标源码/测试后，第 28 次请求等待约 120 秒，`The operation timed out.` 直接终止整个 run。
- scikit-learn `bcff379` Paw 样本：前 11 次模型调用和 18 次只读工具正常，第 12 次请求从 04:31:11 等到 04:33:11，随后整个 run 被记为 `Run aborted.`。manifest 的 25 分钟总预算确实正确传入，故不是 5 分钟隐藏总上限。

orchestrator 对每个请求创建内部 `AbortSignal.timeout(120s)`，再与父级 lifecycle signal 合并。provider 收到任一 signal 后都抛通用 `AbortError`；现有错误分类器既看不到 timeout 字样，也无法知道是哪一个 signal 触发，于是把内部瞬时超时当成不可重试错误，外层又把所有 `AbortError` 当成用户/总预算取消。一次模型网络卡顿就会丢掉整个长任务。

### 设计不变量与改动

- 父级 signal aborted：立即终止，不重试，保留用户取消/总墙钟的确定性。
- 内部 request timeout 先触发且父级未取消：转换为具名 `ModelRequestTimeoutError`，进入已有 `timeout` 分类与最多 3 次退避重试；不清空上下文、任务状态或工作区。
- 不新增针对 DeepSeek/SWE 题目的条件分支；该机制适用于所有 provider/任务。
- 单请求默认仍是 120 秒，只修失败语义；新增可注入 `modelRequestTimeoutMs` 仅用于测试和明确运行时覆盖。

## 2026-08-13 开工冻结：Paw vs Claude Code 公共评测与架构演进闭环

### 目标与结束标准

产品目标固定为：在双方都使用最新版 `deepseek-v4-flash` 的前提下，Paw 的上下文/记忆能力超过 Claude Code CLI，真实 coding 任务完成能力达到或超过 Claude Code CLI。比较不是终点；若 Paw 落后，必须从失败轨迹提取共性根因，形成架构设计、测试和回归证据后再改，禁止为单题堆条件分支、调提示词碰运气或用评测答案做补丁。

本轮只有满足以下证据链才可称为完成：

1. 同模型、同题目、同仓库 commit、同 verifier、同权限和同资源边界的双 runner 可复现；
2. 公共 coding benchmark 的冻结未见 holdout 上，Paw 对 Claude Code 至少达到预先声明的非劣标准；
3. SWE-Exp/MemoryAgentBench 证明记忆对真实修复和官方记忆维度有稳定正效应，而非只在内置夹具有效；
4. 公共或可公开复现的长任务中，Paw 能跨压缩/恢复维持约束、进度和验收闭环；
5. 原始轨迹、patch、官方 verifier 结果、版本与失败样本全部保留，不挑结果。

## 2026-08-12 计划冻结：5 个全新 memory-off 复杂题

### 目的

先测 Paw 在**不使用长期记忆**时，能否稳定完成陌生复杂 coding 任务；基础能力尚未稳定前，不用严格 token 成本作为淘汰门槛，也不把 memory on/off 混入本轮结论。

### “全新”定义

- 必须来自固定版本 SWE-bench Lite，且从未被 Paw 的 agent 实跑、调试、配对或历史 seed 使用。
- 已明确排除：`sphinx-doc__sphinx-8282`、`8435`、`8721`、`11445`、`8801`，`pydata__xarray-4493`，`matplotlib__matplotlib-25332`；生成题单前继续扫描全部历史 run 去重。
- “全新”仅指对本项目/Paw 轨迹未见；公开 benchmark 无法保证基础模型训练时从未见过。

### 入选与基础设施预检

正式抽样前只做**无模型、无 gold 内容审阅**的预检：

1. base commit 可创建隔离 worktree；
2. Docker 镜像可启动；
3. 官方 test patch 可正确安装；
4. 原始代码确实复现 FAIL_TO_PASS；
5. PASS_TO_PASS 可运行；
6. Windows LF/UTF-8 verifier 通路正常。

预检失败记为 `infra_excluded`，只允许在模型运行前由预先冻结的备用题替补。模型一旦开始运行，任何 unresolved、空 patch、超时或实现错误都必须保留，**禁止失败后换题**。

### 复杂度与覆盖规则

- 使用 agent 运行前可见的题面、测试标识和仓库元数据筛选，不按 gold patch 大小或答案实现筛题。
- 至少 1 条 FAIL_TO_PASS、至少 5 条 PASS_TO_PASS；题面足够完整，排除明显机械改字、纯文档和单纯依赖升级题。
- 每个仓库最多 1 题，并覆盖框架、数据类型、符号计算、Web/CLI、配置/Unicode 等不同失败类型，避免集中在 Sphinx/autodoc。

### 冻结物与运行规则

## 2026-08-12 决策：能力优先，SWE 长任务默认撤下严格阶段预算

### 实跑中发现并修复的控制面问题

1. 官方 JSONL 的 `FAIL_TO_PASS/PASS_TO_PASS` 是 JSON 字符串，单题探针未标准化，导致第 0 步异常；现已统一解析。

## 2026-08-12 实验：coding 阶段预算 / 导航熔断

### 机制

- 仅对同时带 `[require_mutation] [coding_phase_budget]` 的实验任务启用；SWE-Exp 曾自动带标记，现已从默认链路撤下，日常 coding 也默认不启用。
- 10 次 grep/read/glob/list 等导航仍无源码编辑 → 注入收敛提醒。
- 14 次后继续导航 → `E_CODING_PHASE` 拒绝，要求做最小候选编辑。
- 有源码编辑后，最多再导航 4 次；仍未测试则强制进入 verify。
- 连续两轮违反阶段要求 → 专用 hard-stop，不能被其他成功工具重置。

### 同题复测（Sphinx 8435，32 步）

| 指标 | 原首对 | 阶段预算复测 |
|---|---:|---:|
| off model calls | 32 | **21** |
| off tokens | 675,045 | **470,114** |
| off patch | 空 | 空 |
| off wall time | 105,623 ms | **420,134 ms（恶化）** |
| on recalled | true | true |
| on patch | 1,254 chars / resolved | 2,054 chars / **未 resolved** |
| 新 on 官方测试 | — | PASS_TO_PASS 16/16；FAIL_TO_PASS 0/1 |

## 2026-08-11 优化：AR/TTL「伪召回」对策（不重跑 LRU）

1. **噪声套件结构性失效（缺陷 A，用户拍板方案）**：semantic 种子会被 task_start 的 episodic/profile 召回规则过滤掉（TRIGGER_KINDS），噪声套件永远测不到。用户选择"种子改 episodic（推荐）"。做法：把 `seedViaPipeline` 重构为接受结构化 `SeedCandidate`（`{kind:"semantic",fact,keywords} | {kind:"episodic",whenToUse,perspective,modification}`）；`NOISE_FIXTURES`/`NOISE_POLLUTANTS` 全部改为 episodic 形态（whenToUse "When X, do Y"、perspective ≤2 句、modification 1-3 项）。
2. **counterfactual 死代码**：删掉被丢弃的首个 backbone 直接回答调用，保留 evidence-based 调用。
3. **ng-08/09 召回失败（真实运行暴露）**：NGram trigram 匹配要求精确 3-char 重叠，"同步"/"字段"都是 2-char 不命中。给 keywords 补真正共享 trigram（"同步读"→"同步读个文件"、"字段名"→"改个名"），重跑 10/10 召回。
4. **单测编写中的 3 个假失败**：`resolveLlmConfig` 测试用了不存在的 cwd（真实调用 findSettingsFile）→ 改真实临时目录 + beforeEach/afterEach；`findSettingsFile` 超 4 层用例路径算错（b 在 i=4 恰好命中）→ 把 startDir 加深到 `a/b/c/d/e/f/g`；env 回退分支读到了同目录残留 settings → 先 `rmSync` `.paw`。

### 突发问题：全量测试 3 fail（非本次改动回归）
keyword 修复后全量 `bun test` 出现 **303 pass / 3 fail**，三处都是 reindex 冒烟 `report.failed` 应为 0 实为 4。排查过程：
1. 先查 DB 残留：redteam-* 为 0，但共享测试库 `paw_memory_test` 里有 **4 条 `type=task_summary`、scope=`ws:*`** 的条目，且已带 embedding。
2. 查来源：`seedViaPipeline` 只产 `redteam-*` scope，不是它。用 title（"update config.json"、"write file 'secret.txt'"、"run shell 'echo paw-cap-test'"）反查，定位到 **agent 包测试**（`packages/agent/test/capabilities-integration.test.ts`、`orchestrator.test.ts`）——它们用 `workspaceRoot`（无 git remote）→ `resolveRepoId` 派生 `ws:*` scope，往**同一个** `paw_memory_test` 库写 task_summary 且不清理。
3. 为什么炸在 reindex：reindex 冒烟扫全表（`t_invalid IS NULL AND 非降级`），遇到 `task_summary` kind 时 `embeddingInput` 无对应分支 → embed 抛错 → `failed += 4`。
4. 处置：清理这 4 条残留后重跑，恢复 **306 pass / 0 fail**。确认非本次改动引入的回归，是跨包共享 DB 的测试隔离问题。
