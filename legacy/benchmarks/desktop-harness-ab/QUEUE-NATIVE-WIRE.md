# 原复杂队列任务：max / 128000 原始流复测

2026-09-07，通过真实桌面宿主 `runDesktopNext` 复测原队列任务。主模型 GLM-5.3-Flash，max，初始输出上限 128000；普通模式，环境审计采用与原参数探针相同的默认启用状态，记忆关闭，未强制 tool_choice。Langfuse 显式关闭。

保持原任务文本、独立空 Git 工作区和 12 分钟 / 40 次调用 / 160000 已报告 token / 32 步边界。此次同时包含输出额度及读回证据修复，是当前组合配置的验证，不是单变量性能实验。

## 结果

| 项目 | 结果 |
| --- | --- |
| 运行状态 | aborted，720.072 秒触及外部时间上限 |
| 模型请求 | 3 次，全部 max / 128000 |
| 工具调用 | 前两次模型请求返回 4 次调用，用于查看环境、读取文件 |
| 首次业务文件写入 | 未发生 |
| 独立功能验收 | 0/15 |
| 自带测试 | 未生成 |
| 已报告 token | 10342；第三次被取消的请求没有 usage，不能视作零消耗 |

第三次请求持续 **699.023 秒**。解析前的原始响应包含 **100804 个思考字符**（JavaScript UTF-16 长度），正文为 0，工具片段为 0。约 3.951 秒开始收到思考；后续相邻网络块最大间隔只有 689 毫秒。它持续输出思考，未进入长时间网络静默。

独立 Python 分析确认三次请求的原始工具字段与 Paw 解析结果一致，流式正文/思考计数也一致。第三次请求没有正常 finish reason 或 length，最终由测试的 12 分钟外部时间边界取消；不是 128000 输出上限导致的截断。

早期 `git status` 出现一次 `spawnSync git ETIMEDOUT`，随后模型仍继续读文件。这是独立工具错误，不能解释后续 699 秒持续返回的思考流。

## 结论与下一步

本轮确认：复杂任务失败的主要等待发生在第一次实现之前，服务端尚未发出结构化工具调用。没有发现 Paw 把已经返回的工具调用丢失；完成检查尚未触发，所以读回证据修复不能解决这段等待。

将输出额度放大到模型能力上限没有让本次复杂任务在原时间预算内完成。小任务在相同 max 配置下可以正常调用工具，不能据此认定 max 普遍失效。更值得验证的是把每轮目标限制为一个可以立即执行和验证的小阶段，例如先实现队列核心，再增加持久化，最后补 CLI 和整体测试；是否改善仍需独立实验。
