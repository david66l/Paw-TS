# GLM 参数对照：2026-09-07

**本轮发现：降低到 high 后，模型能较早开始写代码；单独把输出额度从 8192 提高到 32768 没有解决问题。high 是下一轮完整交付验证的候选配置，但本轮三组都不能算完整交付成功。**

## 三组结果

使用真实桌面宿主 `runDesktopNext`，固定普通模式、同一队列任务、全新独立 Git 工作区、相同外部验收器和调度逻辑。每组最多 12 分钟、40 次模型调用、160000 已报告 token；每条件一次，按表格顺序串行运行。

|配置|首次业务文件|外部功能抽查|自带测试|实际停止原因|
|---|---:|---:|---:|---|
|max，原生 8192 起始额度|未出现|0/15|未提供|12 分钟上限|
|high，原生 8192 起始额度|约 88 秒|15/15|21/23|约 258 秒触及累计 token 阈值|
|max，32768 输出额度下限|未出现|0/15|未提供|12 分钟上限|

high 组生成了队列库、持久化模块、CLI、项目配置、README 和三份测试文件。外部固定 15 项抽查全部通过，但这不涵盖全部边界，也不替代自带测试和最终审计。

其两项测试失败分别是：CLI 测试使用 `existsSync` 却漏了导入；快照测试取出高优先级任务后，却尝试完成另一个仍为 pending 的任务。没有修补产物或修改验收器来提高分数。配置中的测试命令和显式文件补测均为 21/23。

## 为什么不是只调大输出额度

原生 max 组读取需求后的请求耗时约 203 秒，产生 8192 输出 token 后以 `length` 截断；没有正文或工具调用。随后原生续写提高到 128000，但仍未在总时间内写出业务文件。

max/32768 组的对应请求耗时约 667 秒，产生 32768 输出 token 后同样截断，没有正文或工具调用。之后的续写又读取了文件，仍未产生业务文件。

high 组读取需求后的请求约 81 秒返回工具调用，生成 4172 输出 token，随后开始写文件。本组全部 11 次调用均未出现 `length`。这是本轮较早进入执行的证据，不能外推为所有任务上 high 都优于 max。

## 用量与限制

|配置|模型调用/用量回执|已报告输入 token|已报告输出 token|已报告总 token|
|---|---:|---:|---:|---:|
|max-native|4/3|15111|8359|23470|
|high-native|11/11|168562|12684|181246|
|max-32768|5/4|53342|32975|86317|

累计阈值在调用之间检查，所以 high 组的一次在途请求使总数越过 160000。两个 max 组均有缺失用量的中止请求；不能据表格认定它们更便宜，也不能直接把包含缓存输入的 token 总数换算成费用。

这是顺序固定、每条件一次的诊断实验，存在采样与时延波动。high 的停止由评测器累计阈值触发，不代表日常桌面必然在相同位置停止。本轮也没有测试长任务 Manager、中断恢复或原生窗口交互。
