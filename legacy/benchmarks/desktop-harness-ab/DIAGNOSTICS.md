# Diagnostic findings before the valid pilot

These are implementation/setup observations, not performance claims. See the latest protocol-v3 run for actual A/B measurements; v1 and v2 records are explicitly excluded.

1. **Windows workspace-root false rejection (fixed).** Runtime resource keys are lowercased on Windows. `isPathInsideRoot` compared the original strings, then rejected the empty relative path that Windows returns for equivalent differently-cased roots. The child path-policy pass therefore rejected listing/searching the workspace root. A direct reproduction returned sameRoot=true, canonicalCaseRoot=false, childPath=true. The fix recognizes an empty relative path as the same root. Regression coverage checks case equivalence, sibling/parent rejection, scoped policies and symlink/junction escapes.
2. **Benchmark Git isolation (fixed in protocol v2 onward).** Ignored fixture directories under the Paw Git repository did not survive child worktree creation. Protocol v3 places each fixture outside Paw and commits its seed in an independent Git repository. The parent Git root is asserted before any model call.
3. **Output cap (benchmark override removed in v3).** Advertising an 8192-token model ceiling artificially constrains native recovery. V3 passes through the real model capabilities and request settings. Separately, the real desktop context planner currently sets `maxOutputTokens` from its 8192-token reply reserve. The generic recovery policy's 32000 default does not replace an explicit request limit. This interacts with GLM `max` reasoning and requires its own future tuning experiment.
4. **Delegation contract feedback (not changed).** The queue diagnostic repeatedly received `acceptance must be a bounded string array` and `Task task context exceeds the child goal limit`. The public schema includes per-field limits, but the assembled goal + scope + acceptance must additionally fit 4000 characters. The generic errors do not report actual length or the precise failing item. Repeated identical invalid submissions consume budget without execution.
5. **Planning overhead and capability mismatch (not changed).** Managers requested exhaustive repository inventory, verbatim requirements and Git/Node confirmation before implementation. Some requested checks require Shell, which the selected read-only specialist cannot use. Preliminary stages were repeated. This is a separate concern from the confirmed audit exception below; an unknown audit result is not proof of unmet criteria.
6. **Nested read-only auditor cannot start (reproduced offline; not changed during A/B).** The valid long runs contain `AuditUnavailable`. `diagnose-readonly.ts` replaces only the model with deterministic replies and intercepts the audit boundary without changing production code. Both short and verbose worker reports reproduce `Duplicate or empty permission rule id: deny-child-write`, with zero auditor model calls. `preparePawNextReadOnlyChildV3` inherits hard/admin parent rules, then appends its own `deny-child-write` and `deny-child-shell` rules. When the parent is already a read-only child, these IDs already exist. The permission engine rejects the duplicate during nested auditor construction; the environment reviewer catches it and emits the generic `AuditUnavailable`. The reproduction identifies a concrete failure path, not necessarily every cause of that generic code. A fix must preserve inherited denials and handle semantic duplicate rules, rather than dropping parent security policy.

All model settings and main application credentials remain unchanged. The Windows fix is shared by both valid comparison arms. Fixes to planning, delegation feedback or reply budgeting must be evaluated in a separate subsequent experiment rather than inserted into a running pair.

Post-pilot update: the nested auditor rule collision and delegation length feedback were fixed after all six v3 runs settled. Deterministic desktop probes and 135 relevant tests passed; see [POST-FIX.md](POST-FIX.md). The observations above describe the original pilot. The six-case paid-model retest is now complete: the original startup error disappeared in these samples, but no new functionality was delivered. See [RETEST.md](RETEST.md) for results and limitations.
