## 新结果修正了什么

不能把上一轮解释简化为“system 放在前面就失效，放到末尾就解决”。同一位置对不同规则的表现不同；同一规则在两个位置也可能表现不同。指令的作用范围、措辞、与原任务的关系以及上下文共同影响执行。

本轮增加 `--placement` 和 `--persistent`，在出现工具后继续收集到响应结束，以验证完整调用和额外调用。与之前只收集首个工具片段的实验相比，第一片段时刻仍可对照，但现在能够区分“开始调用”和“严格遵守要求”。没有执行任何返回的工具。

| --- | ---: | --- |
| 原“仅下一条响应”指令，追加为末尾 system | 4.112 秒 | 4.247 秒正常结束，唯一完整调用为 node --version |
| 同一句指令，追加到历史中的原 user 消息 | 120 秒内无 | 18916 个思考字符，时间边界取消 |

唯一严格符合“只调用一次指定工具”的是第一行。第四行虽开始指定操作，但有额外调用，不能算完全遵守规则。所有正常完成的结果 finish_reason=tool_calls；超时臂没有 usage，实际 token 消耗未知。

## 哪些解释已被削弱

- **不是必须换成 user 角色才有效。** 末尾 system 也能返回完整正确调用；早期 user 并未促成调用。
- **不是开头的 system 完全失效。** 明确的持续规则放在开头也能较快启动指定调用，但本例有多余调用。
- **删除历史思考不是充分修复。** 实验仅移除两条助手消息的 reasoning_content，共 2045 个字符，保留工具历史和其余字段，仍未在窗口内调用工具。
- **“下一条响应”存在作用范围歧义。** 把这种短期指令追加入历史开头，后面已有助手响应，不能与当前末尾指令简单等同。持续规则实验同时改变措辞和约束强度，因此尚不能把差异单独归因于时间指代。

## 发现了具体的来源识别误判

末尾持续规则的实际请求字段是 `role: system`，没有放入 tool 消息。但响应开头明确将其描述为工具输出中的提示注入，表示拒绝遵守，随后重新展开全项目设计。

这证明模型响应对该指令来源作出了与发送字段不符的判断。不能仅根据模型自述判定云端内部如何渲染或缓存消息；尚无法进一步分离服务端模板行为和模型自身的来源识别能力。

该持续诊断规则刻意要求每条响应只检查 Node 版本，与原实现目标冲突，措辞也与一般执行提示不同。它用于诊断，不能直接部署为产品规则。原始 699 秒响应没有这条规则，因此不能将原始长思考归因为此次提示注入误判。

## Paw 代码层核对

- `packages/runtime/src/context/journal-context.ts` 从固定 system 和选出的历史构造请求。
- `packages/models/src/openai-compatible.ts` 按消息顺序序列化，并保留普通消息的 role；没有发现将末尾 system 改成 tool 或移至开头的逻辑。
- `packages/core/src/model-request.ts` 已支持把运行活动证据渲染为末尾 system。活动证据与执行命令不同，不能通过把任意工具内容改标为指令来解决问题。
- `packages/agent-loop/src/agent-loop.ts` 在调用间的安全边界读取新输入、构建请求，随后等待 model.execute 返回。本次一直有思考流的请求没有返回工具，后续执行和常规下一轮引导无法开始。现有输出恢复也要等请求结束后才处理截断。

因此，当前证据把问题限定在两方面：模型在复杂契约下迟迟不结束规划，以及 Paw 缺少针对“持续思考但没有实际行动”的经过验证的干预策略。没有发现工具调用在传输或 Paw 解析中被丢失；system 能影响模型，但仅修改静态提示词不能视为修复。
