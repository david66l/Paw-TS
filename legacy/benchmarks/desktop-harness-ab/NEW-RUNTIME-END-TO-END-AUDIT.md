# Paw 新桌面运行时端到端审计

后续状态：这是修改前的历史审计。已落实的修复、回归及仍未解决的复杂任务问题见 [v8 修复报告](RUNTIME-V8-HARDENING.md)。下列缺陷刻画不能当作本版应满足的行为。

日期：2026-09-07。范围：桌面正常入口、V3 composition、单 agent 主循环，以及长任务 manager/执行器与该循环的连接。不是 CLI 产品验收，也没有切换模型接口。本轮只新增诊断脚本和报告，未修改生产策略。

## 结论

新运行时的日志、权限、恢复和工具执行边界比较完整，但任务推进、请求内停滞处理与交付判定存在缺口。现有 harness 大部分依赖 **模型先结束当前请求**，随后才计算进度、选择下一步或审查完成情况。模型在一个请求内持续思考时，这些控制不会运行。普通桌面的主请求还没有实验脚本里的 12 分钟总时限。

此外，审计实际复现了项目规则未注入、仅承诺行动也被标记完成、Shell 修改未使验证过期、提醒相互遮蔽，以及展示回调影响模型执行等问题。这些发现不依赖更换供应商接口，足以支持优先修复运行时/harness。

需要区分两个结论：已经证实“Paw 没有控制住这段长思考”，但还不能仅凭这次审计证明“是什么让 GLM 在 Paw 中选择思考更久”。前者有代码和真实轨迹证据；后者还需要控制变量实验，不能把相关性当作全部因果。

## P1：请求内部缺监督，生产桌面没有实验总时限

`agent-loop.ts:260,477` 等待 `model.execute()`；`agent-loop-adapter.ts:168` 一直收流，直到完整结束。循环此时不会再次执行 reducer、progress advisor 或 completion review。`composition.ts:6867` 的停滞工具门也只在模型已经提交工具之后工作。

`paw-next-profile.ts` 的 heartbeat 是会话租约心跳，目的是避免并发进程争抢日志，不是模型无进展检测。`run.ts:679,713` 传入用户 AbortController，没有给正常主任务设置实验中的 720000ms 时限。模型持续输出有效 reasoning 不会自动触发轮数上限，因为本轮还没有结算。

真实 GLM 对比轨迹中，第 3 个请求持续约 705.8 秒，117440 思考字符、无工具片段，最后被 **benchmark 外层** 取消。因此不能把“测试能在 12 分钟停住”说成产品已经具有这项保护。

旧参考：`packages/agent/src/orchestrator.ts:655,3518,4028` 有默认 120 秒请求 signal、错误分类、最多 3 次总尝试。旧实现依赖模型适配器遵守取消，且重试同一上下文仍可能重复浪费。不能直接迁移一个固定 120 秒截断：Claude 对照中一个 124 秒请求随后有正常行动。

修复落点：在 composition 的模型执行宿主边界加入版本化的请求监督政策，保持 loop 的原子结算规则。使用已有 `ModelObservationEvent` 的 headers/bytes/thinking/text/tool_fragment 元数据区分阶段；不要读取思考语义，也不要提前执行不完整工具参数。监督器的预算、请求中断原因、重试计数及未知用量必须进入可恢复的事实记录。只允许明确定义的有限恢复；没有行动的重复请求不能无限重启。任务级预算还必须覆盖路由、压缩、审查和记忆辅助调用。

## P1：自然停下不等于完成，默认审计也会漏过

`packages/agent-loop/src/interactive-control.ts:285` 在无工具、存在可见文字时按 `naturalStop: complete` 返回 completed。`composition.ts:5222` 随后用修改次数、验证证据等决定是否需要构造审查候选。`environment-audit.ts:388` 在没有审查 claim、没有特定写工具观察时投影为 `not_required`。

实际桌面 V3 复现：用户要求 `Create src/main.js that exports the number 42.`；假模型只答 `I will now create the requested file.`。没有创建文件，没有工具调用，结果仍为 `ok:true/status:completed/acceptance:not_required`。关闭审计与默认开启审计两种配置都复现。没有运行真模型或修改用户项目。

旧参考：旧生命周期通过 TaskState、验证门与明确的完成动作处理交付；见 `packages/agent/src/lifecycle/completion-policy.ts`、`verification-gate.ts`。这些任务级语义没有被新 reducer 的 natural stop 等价替代。

修复落点：区分模型回合结束、待验收交付、任务完成。为执行型任务保存轻量的交付要求与对应证据；没有动作/证据只能形成未完成候选或一次有界继续，不能因零修改跳过检查。对解释、咨询等任务保留直接回答能力，不能用一个工具调用数量阈值代替任务语义。修复应在 completion gate/任务契约层完成，不向最小 loop 塞入 benchmark 关键词或要求每个回答必须调用工具。

## P1：旧项目规则与环境注入没有迁移

新入口 `paw-next-profile.ts:42,78` 只加入 `.paw/skills` 目录与通用 agent 提示词，没有旧路径中的 `loadPawMd()`、`loadProjectMemory()` 和环境章节调用。

在临时项目分别写入独有标记的 `PAW.md`、`.paw/CLAUDE.md`、`.paw/CLAUDE.local.md`，捕获真实桌面 V3 首次模型请求：三个标记全部缺失。模型仍可自行发现并读取文件，但当前上下文既不自动提供这些规则，也没有等价的具体发现机制。普通主请求也没有旧环境章节；先前 benchmark 通过用户任务末尾额外提供 Linux/Node/Shell 信息，不能当作产品本身的能力。

旧可复用位置：`orchestrator.ts:4972,5141,5157`；`packages/core/src/system-prompt/sections/environment.ts:97`。应迁移有来源、作用域、预算和明确权限边界的项目指导与环境描述，不把整个旧系统提示词重新拼回去，也不把项目文件升级为授权来源。只恢复旧版本实际支持的文件，不声称旧版已经完整支持 AGENTS.md。

## P1：修改版本按工具名判断，Shell 写入能漏掉

`progress-advisor/src/projector.ts:16` 和 `composition.ts:4681,5004` 各自维护写工具白名单。`workspace_run_shell` 不在其中。环境验收的 `not_required` 判断也依赖相近的写工具名单。

离线事实复现：文件工具写入 → `npm test` 通过 → Shell 修改同一文件 → 到达收尾窗口。advisor 仍使用旧修改位置，把前一次测试当作最新修改之后的通过证据，发出 `The latest check passed...`。诊断脚本只构造事实，没有真正执行该 Shell。

旧参考：`packages/agent/src/task-state.ts:607` 会消费 Shell 结果里的 `workspaceEffect`，更新 `mutationRevision` 与 Shell 命令版本。不能假设现在每个 Shell 后端都已生成这项证据；完整迁移要先确认/补齐执行层，再由所有消费者共同使用。

修复落点：在工具执行宿主生成统一的工作区变更证据，覆盖直接编辑、Shell、撤销、后台任务与子任务；进度、测试新鲜度和完成审查读取同一版本。无法证明影响范围时按“变更未知”处理，避免保留旧验证为当前。只用正则猜 Shell 是否写文件不够可靠。

## P1：新模型端口丢失可恢复错误分类

`agent-loop-adapter.ts:86` 把未取消的异常统一变成 unknown；`interactive-control.ts:241` 将其变为 incomplete。模拟 429、503，均只调用一次并得到 unknown。

旧 `orchestrator.ts:4028` 已有分类、退避与有限尝试。适合迁移的是错误语义和有界机制，不是把所有 unknown 都改成 retry。只有明确拒绝/未产生可执行结果的情况才能按政策重试；断流、模糊副作用和未知响应仍必须保留未知。新请求尝试要有独立身份，不能隐藏在一条成功日志下面。

## P2：收尾提醒被验证提醒遮蔽

`projector.ts:160` 先返回 verification_repair；`192` 的 convergence_checkpoint 只在精确剩余窗口或剩余两轮触发；`362,374` 的 timeline 又对重复 repair 去重。因此 repair 可以先抢占阈值，再被去重丢弃，最后该轮什么新提醒也没有。

复现：总预算 10 轮；第 1 轮写入，随后反复改变测试输出过滤器，到剩余 4 轮和 2 轮时都满足 repair。最终 timeline 只有第一条 repair，收尾提醒数量为 0。

旧 `packages/agent/src/lifecycle/loop-guidance.ts:35` 生成候选列表，收尾指导在窗口内按证据生成，不只依赖两个精确等式。应迁移“多个独立候选＋证据去重”的结构；预算提示与验证修复可以合并表达，不能互相消失。政策改变需要更新 manifest 身份和对应哈希测试。

## P2：提醒没有预留上下文预算，压缩没有累计成本控制

`composition.ts:1915` 先规划普通历史，再判断所有 advice 是否能放进 hard headroom；放不下时整批不加入。历史锚点被压缩或省略后，与它绑定的提醒也可能消失。当前实现没有证明最新关键预算/收尾信息一定交付给模型。

`packages/context-compaction/src/policy.ts:37` 的触发主要看窗口比例与内容省略，不看累计重复输入成本。大窗口下可能多轮重放大量历史却仍低于压缩阈值。已经完成的 reasoning 也会作为协议历史回传；不能为了省 token 直接破坏供应商要求的工具回合配对。

修复落点：在 context plan 内为少量最新运行状态保留固定预算，旧提醒仍可随 checkpoint 归档；记录实际交付的建议。压缩成本政策应区分缓存输入、未缓存输入和摘要/校验开销，采用冷却期和次数上限，而不是每轮总结。

## P2：展示流与推理执行耦合，而且重复发送全文

`agent-loop.ts:480`、`agent-loop-adapter.ts:171` 会 await 展示回调。回调抛错可把模型调用变为 unknown；回调不完成就阻塞下一次流读取。两种行为均已用可释放的有限假流复现，没有遗留挂起进程。

`apps/desktop/agent-host/paw-next-events.ts:89,103` 每次思考 delta 都发送累计全文，调用方错误直接传播。1000 个四字符片段，最终内容 4000 字符，累计事件文本 2002000 字符。按上一轮 GLM 的 28431 个片段推算，全文重复模式会产生约 17.14 亿字符的事件文本；这是根据实现推算的量，不是测得的原生 IPC 流量，不能据此断言这次 benchmark 被 UI 拖慢。

修复落点：模型侧维护增量事件，界面按固定频率合并更新；完整结算/持久化使用另一条有保证的通道。隔离可丢失的展示/监控回调错误，不能吞掉 canonical journal 写入失败。旧运行时也有累计 thinking 事件，因此性能问题不是新架构独有。

## P2：辅助调用与任务收尾仍在关键路径

主模型轮数限制不等于实际 API 调用上限。分类、checkpoint 生成与语义校验、完成审查、记忆抽取/整理可能额外调用模型。`composition.ts:2673,3880,3902` 在返回最终结果前 await 记忆结算；虽然异常被捕获，等待本身没有因此变成后台工作。

修复落点：统一记录这些调用的阶段、预算归属和期限。任务交付结算与可延后的记忆整理分开，后者使用可恢复的有限后台队列，而不是无人跟踪的 Promise。路由失败降级已存在；压缩和记忆调用也需要明确降级/取消行为。这个问题在本次关闭记忆的 GLM benchmark 中没有触发，不能当作那 11 分钟的原因。

## 修复顺序与验收门槛

1. **完成语义与真实变更证据**：执行请求不能凭承诺完成；Shell 修改使旧测试失效；保留咨询任务直接回答。先把这些探针改成期望行为测试。
2. **统一请求监督与预算**：纯思考、无字节、工具参数传输分别测试；取消后零工具副作用；恢复后次数不重置；辅助请求也计入预算。不要默认取消每个 120 秒请求。
3. **恢复项目上下文、修复提醒组合与预留预算**：项目规则按作用域进入请求；验证/收尾同时满足时都能表达；压缩后仍保留当前关键状态。保持通用 agent 身份。
4. **界面增量与辅助收尾隔离**：展示断开不能改变模型结果；长流的传输规模随新增内容增长；任务完成不被可延迟记忆整理拖住。
5. **同模型、同接口复测大小任务**：先一次写入/读取、局部修复，再完整 queue。要求完整验收、直接测试与最终交付全部通过；计入未知用量，重复样本后才比较效率。

不需要重写日志内核，也不需要先引入另一个规划 agent。保留当前确定性执行边界，在宿主层补齐轻量的任务状态、监督和交付判定，才符合单 agent 先做好、之后再扩展多 agent 的方向。
