## 参数与 system prompt 的关系

核对了[官方公开 chat template](https://huggingface.co/zai-org/GLM-5.3-Flash/blob/main/chat_template.jinja)（页面版本 690b705）：它将 reasoning_effort 渲染为额外的 system 消息；保留已有 system 消息，并另行渲染工具定义。也就是说，在该模板下，档位本身也会形成模型可见的指令，不只是 Paw 自己写的那段提示词。

模板在同一个最新用户回合内保留已有助手思考，即使 clear_thinking=true 也是如此。原第三次请求的两条助手消息都在最后一条用户消息之后，因此不能简单推断切换 clear_thinking 就能清除这部分计划。

上述是公开模板的可验证行为。云端 API 的内部模板、缓存和推理实现不可见，不能断言其部署与开源文件完全相同，也没有证据证明服务端忽略 system 消息。

## 指令冲突检查

检查实际传出的 system 消息与全部工具说明，未发现“先完成整个设计才能调用工具”的要求。原任务要求小而完整的实现；工具说明允许正常读写。当前更符合证据的描述是：模型在宽泛目标和未明确的边界上持续展开规划，具体原因需要区分档位、当前任务契约和历史上下文的影响，不能只凭一段短 system prompt 归因。
