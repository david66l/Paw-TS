## 原始响应显示什么

见 [QUEUE-NATIVE-WIRE.md](QUEUE-NATIVE-WIRE.md)。第三次请求在读取需求后持续 699.023 秒，返回 100804 个 UTF-16 思考字符，正文和工具片段均为零。数据持续到达，最终由外部 12 分钟预算取消，没有输出额度耗尽的 finish reason。

内容分析发现：

- 首次写入前就在思考中规划并起草队列核心、持久化、CLI、package.json、README 和整套测试。
- 反复讨论未明确约定的键类型、ID 格式、深拷贝、函数/代理/特殊对象、JSON 持久化和隐藏测试，已形成的设计又被重新讨论。
- 多次准备检查 Node 版本或写文件，随后继续设计，没有转化成工具调用。
- 不是逐字重复的简单循环。内容有推进，但范围持续扩大，许多可以通过实际代码和测试解决的问题被留在单次思考中。

原运行目录的 `thinking-content-analysis.json` 保存独立词法统计：`hidden test(s)` 13 次、`structuredClone` 57 次、三反引号标记 103 个。词频仅辅助定位；103 个标记不等于 103 个代码块。

前一轮响应已明确跳过 Git 超时并继续读需求，该工具错误无法解释后续整段持续思考。

## 参数与结论边界

实际请求带有 25 个工具，包括文件写入和命令工具；未指定 tool_choice。参数为 max、max_tokens=128000、thinking enabled、clear_thinking=false、temperature=1、top_p=0.95、tool_stream=true。系统提示没有禁止执行或要求完成全部规划后才能行动。

[官方模型卡](https://huggingface.co/zai-org/GLM-5.3-Flash)说明 reasoning_effort 控制思考预算，支持 low/high/max，默认 max；clear_thinking 默认 false，聊天场景建议显式 true。它没有承诺 max 在每个代理任务上都更快或可靠。官方不同评测使用不同采样配置，不能仅凭 top_p=0.95 判断适配错误。

可以确认不收敛的规划行为；不能直接证明训练层原因，也不能把失败单独归因于 max、保留思考、某一采样参数或工具数量。扩大输出额度不会强制模型更早切换到工具。

## 桌面接线错误与修复

前端省略任务模式时，Electron 保留省略状态，但 `agent-host/run.ts` 曾把它填成 standard。`paw-next.ts` 只有在模式未指定时才调用 arrangeDesktopTask，因此日常桌面入口绕过了自动模式判断，无法自动进入长任务 Manager 的分阶段委派。

修复：宿主保留未指定状态；显式 standard/long 仍原样传递。未修改 Manager 策略、模型档位或阶段验收规则。

真实宿主 JSON 协议回归测试验证：不传 taskMode 时，本地模型服务收到一次分类请求，然后继续正常执行和处理运行中输入。桌面宿主、输入边界、分类相关 26 项测试全部通过；桌面 host TypeScript 检查通过；新增脚本 Biome 检查和所改宿主/测试文件 diff 空白检查通过。现有 pawNext.test.ts 有本次改动之外的 lint 问题，未宣称全仓 lint 通过。

原 benchmark 显式指定 standard，不经过自动路由。因此该错误解释日常桌面为什么未自动分阶段，并不直接解释 benchmark 的模型行为，也不代表修复后复杂任务已经完成。模型分类仍可能失败并回落普通模式；真实路由选择和分阶段完成率尚需端到端实验。
