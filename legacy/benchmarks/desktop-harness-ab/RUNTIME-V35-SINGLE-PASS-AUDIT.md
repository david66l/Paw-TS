# V35：保留审查进度与明确未验收状态

## 实测触发的问题

[V34 后续实验](RUNTIME-V34-WORKFLOW-RETEST.md) 的产物通过 34/34 独立验收和 55/55 自带测试，但两个各 120 秒的审查都超时。主执行器没有被重跑；审查重试创建新 child，重新读取证据，已知审查开销 167,653 tokens，另两次中断用量未知。

另一个实际展示问题：桌面最终 JSON 正确标记 incomplete/unverified，但 message 以执行模型的“All work is complete and verified”开头，未验收说明只附在后面，容易误导。

## 修改

- 新标准桌面对话使用一次连续的 **240 秒**审查，保持 12 次审查模型回合上限。其最大墙钟分配与旧的两次 120 秒相同，减少在中点中断并丢弃已读上下文的机会。240 秒是整个审查的上限；任务总截止和用户取消仍能提前终止它。
- 到达时限后不自动重启审查、不重新打开主执行工作项，验收保持 unverified。原有模型调用、权限、文件指纹和证据有效性检查不放宽，工具空回答仍使用原语义审查。
- 真实审查进一步暴露了引用未读文件的问题：新策略对 failed/unknown 的审查结果同样停止，不把报告自身的证据错误当作代码缺陷交给主执行器反复修复。明确的 `completed/block` 仍会进入有依据的修复流程。缺失读取会列出具体文件，并写入 unmetCriteria；诊断不再沿用模型自称已完成的摘要。
- 新审查提示说明共享总时限、可批量读取独立文件、可复用范围匹配的新鲜验证，以及证据不足时应指出缺口。没有增加模型调用或常驻服务。
- `environmentAuditSinglePass` 记录在桌面运行索引、V3 profile/task options 和 manifest。只有新标准会话默认启用；旧会话保留原 120 秒/重试身份，历史恢复不能切换策略。长任务 manager 的策略本次不改变。宿主可在创建会话时显式使用旧策略，不新增界面开关。
- 未验收的最终完成消息由主机明确说明状态；审查超时说明“独立验收达到时限”，不会再用执行模型的成功声明作为最终完成消息。原始回答仍保留在日志中。

代码位置：`apps/cli/src/paw-next/environment-audit.ts`、`composition.ts`、`product-profile-v3.ts`、`product-manifest-v3.ts` 和 `apps/desktop/agent-host/paw-next.ts`。

这是对已观察到的审查超时与重复读取的修复，不是对 GLM 长思考的根因判断；240 秒依然可能不足，单次策略也可能失去重试偶然更快的机会。

## 验证

审查、profile/manifest 与生产桌面集成 **43 项通过**，预算、旧会话恢复、读回证据、运行时及审查控制器兼容验证 **32 项通过**，共 **75 项、0 失败**。CLI 共享运行时、桌面前端和宿主 TypeScript 检查通过。

重点覆盖：新会话只安排一个 240 秒定时器；时限取消后不产生第二个 child 或额外 root 请求；文件保留；未验收消息不包含模型自称成功；恢复不重放也不切回旧策略；新策略身份区别于旧 manifest；旧审查重试与崩溃恢复仍保持原行为。

测试把审查定时器压缩为 3 秒，真实执行桌面宿主、只读工具、日志和恢复路径，不调用云端模型。

## 真实验证

`.runs/2026-09-09-v35-workflow-verification` 从 V34 后续实验的十份哈希验证产物创建独立副本，以同一完整任务通过新桌面策略继续验证。保留 GLM-5.3-Flash high、Docker、原验收标准与 20 分钟外层上限。

这份输入已经有正确实现，属于已存在产物上的验收实验，不是从空白完成任务的成绩，不与 Claude/ZCode 的原始成绩直接比较。它在 **160.144 秒、8 次请求、87,374 tokens** 后返回 completed/not_required，独立验收 34/34、自带测试 55/55。因为没有代码修改，现有轻量审查规则未触发独立环境审查，不能将其视为新审查策略实测通过。

随后使用 `audit-live-probe.ts` 回放 V34 后续实验的 21 次主执行决策，通过真实桌面宿主和 Docker 工具恢复完全相同的十份文件，只有独立审查发出新的 GLM 请求。工具定义与模型参数逐请求匹配；不声称请求上下文逐字相同。回放的历史用量不计入新增消耗。报告工具将回放、实际网络请求和被诊断脚本拒绝的请求分别记录。

| 只读审查样本 | 实际模型请求 | 审查模型请求耗时合计 | 新增已知 tokens | 主机接受结果 |
| --- | ---: | ---: | ---: | --- |
| `.runs/2026-09-09-v35-live-audit` | 4 | 67.124 秒 | 59,430 | AuditEvidenceMissing |
| `.runs/2026-09-09-v35-live-audit-confirmation` | 7 | 151.926 秒 | 136,087 | AuditEvidenceMissing |

两次均只有一个连续审查 child，没有审查超时，全部真实调用均有用量；第二次模型请求合计已超过旧的 120 秒单次时限。两次报告都声称 complete，但首份引用未读的 `test/snapshot.test.js` 和 `README.md`，第二份引用未读的 `test/snapshot.test.js`。主机正确拒绝，未将模型声明当作验收。

这两个样本在最终控制修复前运行：旧逻辑尝试回到主执行器，诊断脚本拒绝了那次额外网络请求，分别留下一个本地 rejected 请求；它们既不是云端消耗，也不是审查超时。之后增加的回归先复现了 4 次 root/3 次 audit，再验证修复后为 2 次 root/1 次 audit、恢复零新增调用，并且明确提示未读文件。这个停止修复有生产桌面集成验证，没有再付费重跑同一题。

所有最终产物仍通过 34/34 独立验收和 55/55 自带测试，但真实复杂任务的独立审查**尚未获得可信通过**。不宣称完整链路稳定完成、降低了实际费用或超越其他产品。剩余问题是模型将执行器历史中的读取误当作自己的读取；不应以删除错误引用或放宽证据要求的方式自动宣告成功。
