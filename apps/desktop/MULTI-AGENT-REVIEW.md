# 桌面多 agent 设计检查

2026-09-07。目标：轻量、大小任务统一执行、长任务可靠完成。本次检查 Paw Next 的实际桌面组合与协作代码；没有调用真实模型、修改用户配置或更改调度行为。

## 已核对的现状

实际加载花名册包含 11 个 worker 候选，workspace_delegate 的完整工具定义为 5503 个字符。固定种子包含三个近似相同的编码角色（bianmu/demu/samo），均使用相同能力、工具集合和 18 次模型调用上限。登记多个角色不会自动启动多个进程，但会增加模型可见的选择与描述。

当前桌面配置没有启用旧 rootPrompt。默认 root 种子仍包含 workspace.run_agent/workspace.create_agent 的旧工具名，切换到相应团队模式时存在兼容性风险；不能把这段未激活的提示词归因于当前长思考。

## 优先问题

### 1. 长任务主 agent 被固定为 Manager

`packages/paw-next/src/long-horizon.ts` 的 LONG_HORIZON_MANAGER_PROMPT 明确禁止主 agent 修改文件或执行命令，要求阶段委派。该设计提供角色隔离，但让小的收尾、修补和验证也需要交接，不符合主 agent 按需决定是否委派的方向。

建议：保留统一主执行器的动手能力；由任务依赖、上下文隔离收益和可并行性决定委派。主 agent 与 worker 的写操作仍须通过工作区协调，不应同时无约束写入。

### 2. 受验收保护的任务批被整体串行化

`packages/collaboration/src/delegation.ts` 的 runMission 使用 `slice(0, validateDependencyResult ? 1 : maxConcurrentChildren)`；composition 在 longHorizon=manager 时提供 validateDependencyResult。因此这一模式中，同一 mission 内即使有独立只读子任务，每批也只启动一个。

普通模式的调度已有只读并行、写任务串行和测试期间保持稳定工作区的保护。不能直接移除验收或提高并发解决问题。应按依赖和证据版本判断哪些只读任务可共享稳定快照，保留必要写入与验收屏障。

### 3. 角色重复，实例与能力混在一起

花名册合并三个通用默认角色和八个动物命名 worker，主 agent 必须显式选择 agent_id。多个实现角色的差别很小；调查/审查/验证也有重叠模板。

建议：少量明确的能力与权限模板，按需创建任务实例。模型选择所需能力，程序分配实例身份；自定义专长保留为可选配置。名称和形象可留在界面展示，不必成为执行调度所需的复杂概念。

### 4. 交接主要靠摘要，已有结构化证据没有充分传递

formatDelegatedGoal 将每个依赖结果压成最多 800 字符单行摘要，并与任务目标、范围、验收共同竞争默认 4000 字符额度。剩余额度不足时，直接省略依赖信息。根任务聚合返回虽然已包含 changedFiles、testsRun、outcome/artifactRefs，但这条依赖输入路径只读取 summary。

建议：交接携带简短结论、修改文件/接口、工作区版本、验证结果和稳定证据引用。大内容按需读取；预算不足时显式给出省略提示及可回读引用，避免静默丢失上下文。复用已有结果结构和持久化存储。

### 5. 预算与续作配置缺少统一解释

全局策略是初始 24 次、每子任务最多 96 次，但实际硬上限取选中 AgentSpec 与全局上限的较小值。三个默认编码角色只有 18 次，因此在这些角色上通常没有可续展的软窗口。18 次不一定不足，问题是相同任务换个重叠角色就会获得不同预算，且调用次数无法限制单次模型长思考。

建议：分别管理阶段调用预算、实际用量和无行动等待；根据验证进展决定是否续作。不能把全局 96 次误当成每个角色都能使用的额度，也不应一律提高上限。

## 建议收敛的产品形态

- 一个有完整执行能力的主 agent，始终负责用户目标和最终集成。
- 按需调用的 worker，每个任务有范围、依赖、权限和验收要求；小任务不增加协作调用。
- 共享一份持久任务记录和证据索引，各 worker 保持独立上下文，减少重复阅读和互相干扰。
- 调查可在稳定版本上并行；默认保留一个写入者。必要时才引入隔离工作区，且必须验证合并后的整体结果。
- 优先使用现成测试、构建和行为检查；独立模型审查用于需要判断的交付或存在疑点的结果，避免每个微小步骤都重复增加模型调用。
- 子任务结束后可针对明确问题继续或修复；恢复要沿用成果和证据，不等于从头委派同一个模糊任务。

## 实施顺序与验收

先统一主执行器的任务安排，明确协作契约和证据引用；再调整角色与预算、开放可证明安全的并行；最后与长思考的进展控制结合。权限、稳定调用身份、持久化、取消和证据新鲜度机制继续保留。

用同一批任务比较单 agent 与按需协作：实际完成率、总耗时、模型调用/用量、重复读取、冲突和返工、人工干预次数。当前检查证明设计约束和信息路径存在，并未测得各项改动的性能收益，不能提前声称多 agent 一定更快或已优于其他产品。
