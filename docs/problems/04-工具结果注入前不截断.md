# 04 工具结果注入前不截断（P0-2）

- 状态：方案已定，待实施
- 日期：2026-08-04

## 问题

**现象**：工具结果进上下文时无单条大小检查，单条超大输出（如 500KB 日志）在注入当下即超窗。

**根因**：注入（write-time）与清理（read-time）存在时间差——
1. `finalizeToolExecution`（`tool-runner.ts:514-521`）把完整 payload 原样传入 `ctxMgr.addToolResults`
2. L1 prune（`orchestrator.ts:1325`）在**下一轮** executeTurn 步骤 2 才执行——本轮注入后到下一轮 prune 前，上下文全程超载

**后果链**：
1. `addToolResults` 内部 `maybeTruncate()`（L3）被触发，按优先级**删整条消息**——误伤邻居（可能删掉记录重要决策的 assistant 消息），而不是截断这条超大结果
2. 触发 L2 compact 白烧一次辅助模型调用，还可能因"收益 <15%"被跳过
3. 极端情况直接超 API 窗口 → 400 context length exceeded → 整轮失败
4. 即使不超窗：500KB ≈ 125k token 按输入价计费，一次注入 ~$0.4，且模型只需要头部（错误首行）+ 尾部（exit code），中段滚动日志是噪音

**对照**：Claude Code / OpenHands 都在注入前截断（单条 ~5k token 上限，业界惯例，未逐一验证源码）。这是"write-time enforcement"，比事后清理更根本。

### 结论

1. **时机**：处理应发生在"摄入门口"（TokenPilot 的 ingestion gate），不是事后清理（L1/L2/L3 都是事后）。这是 write-time vs read-time 的学术证据，支撑"注入时截断层"
2. **可恢复性是截断的前提**：ARC / PRO-LONG 说明——如果全文可寻址恢复（日志 01 的"可寻址归档"），注入截断几乎无信息损失。本方案先做截断，可寻址恢复作为后续升级（截断标记带真实损失量，模型可感知"丢了什么、要不要恢复"）
3. **内容取舍**：头部（命令回显/关键首行）+ 尾部（exit code/错误）保留、中间滚动日志丢弃——对应 SWE-MeM / C AT 对"noisy trajectories"的观察：信息不对称分布，中间段是噪音
4. **截断 ≠ 丢弃**：`...[truncated N chars]...` 标记让模型知道损失规模，可选择换命令只取关键部分——与事后 L3 的"整条消息误删"有本质区别

## 解决方案

在 `tool-runner.ts` 步骤 3（`addToolResults`）前新增截断层：

```ts
const trimmed = results.map((tr, i) => ({
  tool: calls[i]!.tool,
  ok: tr.ok,
  summary: tr.summary,
  payload: truncatePayload(tr.payload, MAX_TOOL_RESULT_CHARS),  // ← 新增
}));
ctx.ctxMgr.addToolResults(trimmed);
```

- `truncatePayload(payload, limit)`：字符超限 → 保留头部 2k + `"[... truncated N chars ...]"` + 尾部 2k
- **为什么保留头尾丢中间**：失败时 exit code 和错误在尾部，命令回显和关键首行在头部，中间是滚动日志/构建进度（噪音）
- 上限可配（默认 ~10k token ≈ 40KB 字符，进 settings）
- **独立一层**：不依赖 orchestrator 是否记得调 L1；与 L1 关系不变（L1 负责多条旧结果落盘，截断层负责单条不超预算）

风险：低（纯字符串处理 + 一个配置项）。
