# 01 上下文管理：事后清理齐全但缺"注入前"闸门

- 状态：调研完成，待实施
- 日期：2026-08-04

## 问题

**现象**：上下文管理三层压缩（L1 落盘 / L2 LLM 摘要 / L3 优先级驱逐）齐全，但防线顺序放反了——所有清理都是"事后"（消息进上下文之后），没有"注入前"（write-time）防护。单条超大工具输出（如 500KB 日志）在注入当下即超窗，触发下游 L3 误删邻居消息、L2 白烧辅助模型调用，极端情况直接超 API 窗口。

**根因**：
1. `finalizeToolExecution`（`tool-runner.ts:514-521`）把完整 payload 原样注入上下文，无单条大小检查
2. L1 prune（`orchestrator.ts:1325`）在**下一轮**才执行——存在整轮超载窗口期
3. L1 落盘后的预览指针**不可寻址**：agent 无法按 ID 恢复全文，只能看到预览文本
4. L1/L2 从历史**中间**删消息，破坏 prompt 前缀 → prompt cache 失效（TokenPilot 实测成本差 61-87%）
5. 压缩时机由 token 阈值驱动，而非任务阶段驱动

**对照**：Claude Code / OpenHands 都在注入上下文前按预算截断单条工具结果（每条 ~5k token 上限）。

### 业界实践

- Claude Code / OpenHands：工具结果注入前按预算截断（单条上限），保留头尾。
- 六条共识：① 被动阈值压缩不够，要主动/可寻址/生命周期治理；② 压缩必须可恢复（归档而非丢弃）；③ 锚点（约束/计划/用户意图）必须隔离出有损路径；④ 前缀稳定 = 省钱；⑤ 给模型可见性；⑥ 时机由任务阶段驱动。

## 结论

- 本项目"保护锚点"做对了（用户约束 120 分 ≈ Constraint Pinning；计划每轮重注入 ≈ Plans Don't Persist 的解法；L1 落盘是 ARC 的雏形），缺口集中在：注入前闸门、可寻址恢复、前缀稳定、主动压缩时机、模型可见性。
- 优先级：注入前截断（单点改动，立竿见影）> 前缀稳定 > 可寻址恢复 > 主动压缩工具（C AT 路线，长期）。

## 解决方案

1. **注入时截断层**（P0-2，见日志 04）：`addToolResults` 前按预算截断单条 payload（头 2k + 尾 2k + 截断标记，上限可配默认 ~10k token），独立于 L1/L2
2. **前缀稳定**：L1/L2 压缩尽量只动尾部消息，不在中间删消息（配合 prompt cache）
3. **可寻址归档**（ARC 路线）：L1 落盘时给每个结果分配 ID，预览改为可请求恢复的引用（新增工具或让 read 工具支持引用恢复）
4. **主动压缩工具**（C AT 路线，长期）：把压缩做成模型可调用的工具，让模型在子任务完成时主动触发摘要
